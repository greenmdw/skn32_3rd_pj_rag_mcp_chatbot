## 1. 우리가 조사한 Text2SQL 구현 방법 7가지

| # | 방법 | 한 줄 설명 | 우리가 골랐나 |
|---|---|---|---|
| 1 | **시맨틱 레이어** (Semantic/Metrics Layer) | "매출이 뭐다"처럼 업무 용어의 뜻을 DB(뷰)에 미리 못박아두는 방식 | ✅ 선택 |
| 2 | **실행 피드백 자기수정** (Execution Feedback Self-Correction) | SQL을 만들고 실제로 검증해봐서, 틀리면 에러 메시지를 보고 스스로 고치게 하는 방식 | ✅ 선택 |
| 3 | 지식그래프/온톨로지 기반 스키마 링킹 | 테이블이 수백~수천 개일 때, 질문과 관련 있는 테이블만 그래프로 찾아주는 방식 | ❌ |
| 4 | 특화 파인튜닝 SQL 모델 | SQL 생성만 전문으로 하도록 모델을 별도로 학습시키는 방식 | ❌ |
| 5 | RAG 기반 예시 검색 (Retrieval-Augmented) | "질문 → 검증된 SQL" 예시를 미리 저장해두고 비슷한 질문이 오면 참고시키는 방식 | ❌ |
| 6 | MCP 기반 표준 인터페이스 | LLM이 DB·문서 같은 외부 도구를 표준 프로토콜로 부르게 하는 방식 | (필수 기술, 선택지 아님) |
| 7 | 에이전틱 탐색형 (스스로 스키마 탐색) | LLM이 `SHOW TABLES`/`DESCRIBE`를 스스로 반복 실행하며 스키마를 알아내는 방식 | ❌ |

## 2. 왜 1번(시맨틱 레이어) + 2번(실행 피드백 자기수정)을 선택했는가

### 2.1 먼저 탈락하는 방법부터

- **3, 5, 7번**은 전부 "스키마가 너무 커서 프롬프트에 다 못 넣는다"는 문제를 푸는
  기법이다. 우리 sales DB는 테이블 14개, 컬럼 약 220개뿐이라 스키마 전체를 프롬프트에
  그냥 넣어도 부담이 없다 — 이 기법들이 푸는 문제 자체가 우리에게는 없다.
- **4번(파인튜닝)**은 학습 데이터·GPU·시간이 많이 필요해 부트캠프 기간엔 불가능하다.
- **6번(MCP)**은 애초에 선택지가 아니라 프로젝트 필수 기술이다. 무엇을 고르든 결국
  MCP 위에서 구현하게 된다.

### 2.2 남은 1·2번이 서로 다른 실수를 잡는다

Text2SQL의 실수는 크게 두 종류다.

```
실패 유형 A: SQL 자체가 에러가 남           → "없는 컬럼입니다" 같은 에러가 뜸 → 눈에 보임
실패 유형 B: SQL은 멀쩡히 실행되는데 답이 틀림 → 그럴듯한 숫자가 나옴 → 아무도 못 알아챔
```

| 방법 | 막는 실수 | 원리 |
|---|---|---|
| 1. 시맨틱 레이어 | **유형 B** (의미는 틀렸는데 에러는 안 남) | "매출 = 취소·초안 제외한 합"을 DB 뷰에 못박아, LLM이 SQL을 어떻게 쓰든 결과가 항상 같은 규칙을 따르게 함 |
| 2. 실행 피드백 자기수정 | **유형 A** (문법·존재하지 않는 컬럼 오류) | 실행 전 `EXPLAIN`으로 미리 채점하고, 실패하면 MySQL의 실제 에러 메시지를 LLM에 보여줘서 1회 재작성 |

**유형 B가 더 위험하다.** 에러 없이 그럴듯한 숫자가 나오기 때문에 틀렸다는 걸
아무도 눈치채지 못한다. 그래서 1번(정의를 못박는 것)이 이번 설계의 중심이고,
2번은 그걸 보완하는 역할이다.

> 우리 프로젝트 주제 자체가 "환각을 방지하는 RAG 기반 LLM 질의응답 시스템"이라,
> "SQL을 잘 만드는 것"보다 "틀린 답을 그럴듯하게 만들어내지 않는 것"이 더 중요한
> 목표였다는 점이 이 선택의 배경이다.

## 3. 뷰(VIEW) 테이블을 쓰는 이유

### 비유

요리사마다 "곱빼기"의 양을 다르게 생각하면 손님이 매번 다른 양을 받는다. "곱빼기 =
면 200g"이라고 규칙을 정해두면 누가 만들어도 똑같다. **뷰가 그 규칙을 못박아두는
창구다.**

### 핵심 이유 3가지

1. **업무 정의를 LLM의 판단에 맡기지 않기 위해.** "매출 계산에 취소 주문을 넣을지"
   같은 판단을 LLM에게 프롬프트로 "부탁"하는 게 아니라, 뷰 자체에 그 규칙만 담아서
   **애초에 어길 방법이 없게** 만든다.
2. **fan-out(중복 합산) 사고를 구조적으로 차단하기 위해.** 주문 1건에 상세 항목이
   평균 2.7개 딸려 있는데, 헤더 금액과 상세를 그냥 JOIN해서 더하면 상세 개수만큼
   금액이 중복으로 더해진다. 아예 헤더 금액 컬럼을 상세용 뷰에 넣지 않으면 이 실수
   자체가 불가능해진다.
3. **개인정보(PII)를 원천 차단하기 위해.** 이메일·전화번호·주소 같은 컬럼을 뷰에서
   아예 빼서, LLM에게 주는 스키마 정보에도 그런 컬럼이 존재한다는 사실 자체가 안
   나가게 한다.

### 뷰가 만드는 3중 방어 구조

```
1층  MySQL 뷰      취소 제외 · 개인정보 제외 · 헤더-상세 중복 합산(fan-out) 방지를 DB가 강제
2층  DB 권한        조회 계정은 뷰만 볼 수 있고 원본 테이블은 아예 못 봄
3층  SQL 검사       실행 전 문법·안전성 검사 + EXPLAIN 사전 채점
```

## 4. 이 방법의 장점과 단점

### 장점

| 장점 | 설명 |
|---|---|
| 같은 질문 = 같은 답 | 지표 정의가 뷰에 고정돼 있어 LLM이 매번 다르게 해석할 여지가 없다 |
| 에러 없는 오답을 줄임 | 가장 위험한 실패 유형(B)을 코드/DB 레벨에서 원천 차단 |
| 구현 난이도 대비 효과가 큼 | 파인튜닝·스키마링킹 같은 무거운 기법 없이도, 우리 규모(테이블 14개)에서는 충분한 정확도 확보 |
| 보안이 구조적으로 보장됨 | LLM 프롬프트 실수나 코드 버그가 있어도 DB 권한(뷰만 SELECT 가능)이 마지막 방어선 역할 |
| 설명 가능성 | "왜 이 답이 나왔는지"를 생성된 SQL과 뷰 정의로 그대로 추적 가능 (블랙박스 모델이 아님) |

### 단점

| 단점 | 설명 |
|---|---|
| 실행 피드백이 못 잡는 실수 존재 | `SELECT SUM(total_amount) FROM sales_orders`처럼 취소 주문까지 포함해도 문법·실행은 정상이라 EXPLAIN을 통과함 — 오직 뷰(1번)로 미리 막아둔 부분만 안전 |
| 뷰를 늘릴 때마다 사람이 직접 설계해야 함 | 새 지표·질문 유형이 생기면 자동 대응이 아니라 개발자가 매번 DDL을 새로 짜야 함 (유연성 낮음) |
| 뷰 밖의 질문에는 아예 답 불가 | 견적·배송·여신한도처럼 이번에 뷰로 안 만든 영역은 데이터가 DB에 있어도 조회 불가(의도된 제약) |
| 작은 데이터셋 기준으로 검증됨 | 지금은 제일 큰 테이블도 `LIMIT 200`이 사실상 "전체 반환"과 같은 규모. 데이터가 수만~수십만 행으로 커지면 응답 속도·요약 방식을 다시 설계해야 함 |
| "실행 가능함"과 "질문에 맞는 답"은 다름 | EXPLAIN은 컬럼명 오타·문법 오류는 잡지만, "질문 의도를 잘못 이해해서 엉뚱한 뷰를 골랐다" 같은 실수는 못 잡음 |

## 5. 현재 실무에서 쓰이는 방법

> 특정 논문·벤치마크를 확인하고 쓴 게 아니라, 일반적으로 알려진 업계 경향을
> 참고용으로 정리한 것이다. 정확한 최신 사례가 필요하면 별도 조사가 필요하다.

실무에서는 한 기법만 단독으로 쓰기보다, 데이터 규모와 목적에 따라 여러 기법을
조합하는 경우가 많다고 알려져 있다.

- **시맨틱/메트릭 레이어**: 회사의 핵심 지표(매출, 이익 등)를 다루는 곳에서 기본으로
  깔고 가는 경향. "지표 정의가 팀마다 다르면 안 된다"는 요구가 강한 환경(재무, 경영
  보고)일수록 중요하게 다뤄짐.
- **스키마 링킹/예시 검색(RAG)**: 테이블이 수백~수천 개인 대규모 데이터 웨어하우스에서
  거의 필수. 우리처럼 테이블 10~20개 규모면 상대적으로 덜 중요.
- **실행 피드백 자기수정**: 구현 난이도 대비 정확도가 크게 오르는 편이라, 규모와
  무관하게 거의 기본으로 들어가는 경향.
- **멀티에이전트(역할 분리)**: 복잡한 분석 질문을 다루는 고급 시스템에서 쓰이지만,
  LLM 호출이 늘어나 응답 속도·비용 부담이 커서 정말 필요한 경우에만 선택적으로 쓰임.
- **특화 파인튜닝 모델**: 자체 데이터·인프라가 충분한 대기업에서 주로 쓰이고, 작은
  팀·프로젝트에서는 잘 안 쓰임.

**우리가 고른 "시맨틱 레이어 + 실행 피드백 자기수정" 조합은, 업계에서도 가장
기본으로 깔고 시작하는 조합과 방향이 같다.** 3·5·7번(스키마 링킹류)을 뺀 이유도
"우리 규모에서는 아직 필요 없다"는 것이지 "나쁜 방법이라서"가 아니다. 나중에
뷰·테이블이 훨씬 많아지면 다시 검토할 수 있다.

> **참고**: 조사 단계의 표(1절)에서 2번 방법을 "멀티에이전트 + 실행 피드백
> 자기수정"으로 함께 묶어 불렀지만, 실제 구현은 **하나의 LLM이 SQL을 생성하고,
> 실패하면 같은 LLM에게 에러 메시지를 보여줘서 다시 요청하는 단순 재시도(최대
> 1회) 구조**다. 역할이 분리된 여러 에이전트가 서로 검토·토론하는 진짜
> "멀티에이전트" 구조는 아니다 — 발표 때 과장되지 않도록 이 점은 정확히
> 짚고 넘어가는 게 좋다.
