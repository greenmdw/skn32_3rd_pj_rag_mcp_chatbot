# [팀 공유 자료 5] Text2SQL 처리 구조 보고서 (sales·purchase 공통)

- **작성자**: rag_sales 담당 (PM 겸임)
- **목적**: "사용자 질문 하나가 들어왔을 때, 어떻게 SQL을 만들어서 답변까지 나가는지"를
  단계별로 정리하고, 각 단계에 어떤 안전장치가 들어있는지 짝지었다. PPT 구조도 제작용.
- **범위**: sales 기준으로 작성. purchase는 파일·계정·뷰 이름만 다를 뿐 완전히 같은
  구조다(3절 대응표 참고).

---

## 한눈에 보는 흐름 (PPT용 요약)

```mermaid
flowchart LR
    A["① 질문 입력"] --> B["② SQL 생성\n(LLM)"] --> C["③ SQL 검증"] --> D["④ 실행 전 점검"] --> E["⑤ DB 실행"] --> F["⑥ 답변 생성"]
```

**안전장치는 ③~⑤ 세 단계에 걸쳐 4겹으로 들어가 있다** — LLM이 실수로 위험하거나
틀린 SQL을 만들어도, 넷 중 하나는 반드시 걸러낸다는 게 핵심 설계 의도다.

| 단계 | 무엇을 하나 | 안전장치 |
|---|---|---|
| ① 질문 입력 | 사용자 질문을 받는다 | 빈 질문·500자 초과 즉시 차단 |
| ② SQL 생성 | LLM이 질문을 SQL로 변환 | 답할 수 없는 질문은 SQL 대신 "모른다"로 응답하게 설계 |
| ③ SQL 검증 | 생성된 SQL 문장 자체를 검사 | **[안전장치 1] 정적 SQL 가드** |
| ④ 실행 전 점검 | 실제 데이터를 건드리기 전에 미리 채점 | **[안전장치 2] EXPLAIN 사전검증 + 1회 재시도** |
| ⑤ DB 실행 | 실제 MySQL에 SELECT 실행 | **[안전장치 3] 조회 전용 계정 권한**, **[안전장치 4] 뷰에 고정된 업무 규칙** |
| ⑥ 답변 생성 | 조회 결과로 답변·표·그래프 생성 | 결과 0건이면 "없다"고 정직하게 안내 |

## 단계별 상세

### ① 질문 입력

사용자가 채팅창에 자연어 질문을 입력한다. (예: "2025년 4분기 고객별 매출 상위 5개")

- **안전장치**: 빈 질문이거나 500자를 넘으면 LLM을 부르지도 않고 바로 "조회 결과
  없음"으로 끝낸다 — 불필요한 API 비용을 막는다.
- **구현**: `mcp_servers/data_tools/sales/query.py` (`MAX_QUESTION_LENGTH = 500`)

### ② SQL 생성 (LLM 호출)

질문 + "지금 우리 DB에 뭐가 있는지"를 함께 LLM(OpenAI)에게 주고 SQL을 받는다.

- **LLM에게 주는 정보(스키마)를 우리가 직접 좁혀놨다**: 원본 테이블(14개)을 그대로
  보여주지 않고, 뒤에서 설명할 "뷰" 5개만 존재하는 것처럼 알려준다. 그래서 LLM이
  처음부터 원본 테이블 이름을 모른다.
- **지표 정의를 하나로 고정**: "매출"이라고 하면 무조건 `v_sales_order.order_amount`
  하나만 쓰도록 프롬프트에 못박아뒀다(이전엔 "A 또는 B"처럼 모호하게 설명해서 같은
  질문에 다른 답이 나온 적이 있었음).
- **답할 수 없는 질문 목록을 미리 알려준다**: "영업이익", "재고" 등 우리 DB로 계산할
  수 없는 16개 지표를 LLM에게 미리 알려주고, 이런 질문엔 SQL을 만들지 말고 포기하도록
  지시했다.
- **구현**: `mcp_servers/data_tools/sales/schema.py`(뷰·지표 정의), `text2sql.py`(프롬프트
  12개 규칙 + OpenAI 호출)

### ③ [안전장치 1] SQL 검증 (정적 가드)

LLM이 만든 SQL 문장을 실행하기 전에, 문장 자체만 보고 검사한다. DB에 연결조차 하지
않는다.

| 검사 항목 | 걸리면 |
|---|---|
| `SELECT`/`WITH`로 시작하는 문장이 딱 1개인가 | 거부 |
| `INSERT`/`UPDATE`/`DELETE`/`DROP` 등 위험 명령어가 있는가 | 거부 |
| 우리가 허용한 뷰 5개 밖의 테이블을 쓰는가 | 거부 |
| 결과 파일로 빼돌리는 `INTO OUTFILE` 같은 구문이 있는가 | 거부 |
| `LIMIT`이 없거나 너무 큰가 | 자동으로 200으로 고침 |

- **구현**: `mcp_servers/data_tools/sales/sql_guard.py`

### ④ [안전장치 2] 실행 전 점검 (EXPLAIN 사전검증 + 1회 재시도)

①~③을 통과한 SQL이라도, 문법 오류나 존재하지 않는 컬럼을 참조할 수 있다. 실제로
데이터를 조회하지 않고 MySQL의 `EXPLAIN` 기능으로 "이 SQL이 실행 가능한가"만
미리 확인한다.

- 실패하면 → MySQL이 알려준 정확한 오류 메시지를 LLM에게 다시 보여주면서 "이 부분을
  고쳐서 다시 만들어달라"고 **딱 1번만** 재시도시킨다.
- 재시도까지 실패하면 → 더 반복하지 않고 그냥 실패로 끝낸다(무한 재시도로 비용이
  새는 것을 막음).
- **구현**: `mcp_servers/data_tools/sales/mysql.py`의 `ExplainOnlyMySQLClient`,
  `query.py`의 재시도 로직

### ⑤ DB 실행 — 여기서 안전장치가 2겹 더 있다

**[안전장치 3] 조회 전용 계정 (DB 권한 분리)**

실제 SELECT를 실행하는 계정(`sales_reader`)은 **원본 테이블 14개에 대한 권한이
전혀 없다.** 오직 아래 뷰 5개만 볼 수 있다. 그래서 설령 ③번 검사를 어떻게든
피해서 원본 테이블을 조회하는 SQL이 만들어져도, DB가 자체적으로 권한 오류를 낸다
— "혹시 코드에 구멍이 있어도 DB가 마지막에 한 번 더 막아준다"는 이중 안전판이다.

**[안전장치 4] 뷰(View)에 업무 규칙을 고정**

원본 테이블 대신 아래 뷰 5개만 노출해서, "매출 계산에 취소된 주문을 넣을지 말지"
같은 업무 판단을 LLM에게 맡기지 않고 DB 단에서 강제한다.

| 뷰 이름 | 고정된 업무 규칙 |
|---|---|
| `v_sales_order` | 취소·초안 주문은 애초에 안 보이게 제외 |
| `v_sales_order_line` | 헤더 합계 금액 컬럼을 아예 안 줌 → 라인 합계와 이중 합산되는 사고 차단 |
| `v_invoice` | 청구·미수금만 |
| `v_customer` | 이메일·전화번호·주소 등 개인정보 7개 컬럼 제외 |
| `v_sales_order_status` | 취소 주문 현황 집계 전용(다른 뷰는 취소 주문을 아예 숨기므로 따로 둠) |

- **구현**: `database/sales/grants_reader.sql`(안전장치 3), `database/sales/views.sql`(안전장치 4)

### ⑥ 답변 생성

조회된 결과를 LLM에게 다시 넘겨서 자연어 답변을 만들고, 화면에는 표·생성된 SQL·
그래프를 함께 보여준다.

- **결과가 0건이어도 오류가 아니라 "그 조건에 맞는 데이터가 없다"는 사실**로 안내한다
  (예: 아직 데이터가 없는 미래 기간을 물었을 때).
- **구현**: `app/agent/nodes.py`(통합 담당), `mcp_servers/data_tools/sales/query.py`
  (결과 정리)

## 요약: 4겹 안전장치가 막는 것

| 안전장치 | 막는 것 | 비유 |
|---|---|---|
| 1. SQL 문장 검사 | 위험한 명령어·엉뚱한 테이블 접근 | 출입 서류 검사 |
| 2. EXPLAIN 사전검증 | 문법·존재하지 않는 컬럼 오류 | 예행 연습 |
| 3. 조회 전용 계정 권한 | 코드 실수로도 원본 테이블은 물리적으로 못 봄 | 출입증 자체가 안 나옴 |
| 4. 뷰에 고정된 업무 규칙 | LLM이 몰라서/잘못 판단해서 틀린 집계를 내는 것 | 계산기에 공식이 미리 새겨짐 |

## 도메인 간 대응표 (purchase는 이름만 다름)

| 항목 | sales | purchase |
|---|---|---|
| 조회 함수 | `query_sales()` | `query_purchase()` |
| 조회 전용 계정 | `sales_reader` | `purchase_reader` |
| 뷰 5개 | `v_sales_order` 등 | `v_purchase_order`, `v_purchase_order_line`, `v_vendor_invoice`, `v_vendor`, `v_purchase_order_status` |
| 가드 파일 | `sales/sql_guard.py` | `purchase/sql_guard.py` |
