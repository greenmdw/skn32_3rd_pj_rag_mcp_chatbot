**무엇을 고쳤나**

- 모듈 하나당 테스트 하나(`test_module_imports_cleanly[모듈경로]`)라, 깨지면 정확히 어떤 모듈인지 테스트 이름으로 바로 특정됨

- `query.py`의 import를 일부러 오타로 깨뜨려서 재현 → 해당 모듈과, 그걸 참조하는 `server.py`까지 정확히 실패하는 것 확인

## 2. 검색 계층(RAG) 개선

### 2-1. 어휘 하이브리드 점수 재설계 (재인덱싱 불필요)

**왜**: `adversarial_eval.py` 기준 관련 질문 최저 점수와 무관 질문 최고 점수가 겹쳐서
임계값만으로 분리가 안 되던 문제. 원인을 파고드니 `search_text()`(어휘 검색)가 "회사",
"규정"처럼 **거의 모든 문서에 등장하는 상투어 하나만 겹쳐도 고정 0.55점**을 주고
있었음 — "우리 회사 주가 얼마야" 같은 범위 밖 질문도 "회사"만 겹쳐서 임계값을 쉽게
넘어버렸음.

**무엇을 고쳤나**

| 파일 | 내용 |
|---|---|
| `mcp_servers/document_tools/faiss_store.py` | `search_text()` 점수 공식을 검색어별 IDF 유사 가중치 기반으로 재설계. 검색어가 몇 개 문서에 등장하는지 계산해서, 흔한 말일수록 가중치를 0에 가깝게, 소수 문서에만 등장하는 판별력 있는 말일수록 가중치를 높게 줌 |
| `tests/unit/test_document_mcp_eval.py` | 회귀 방지 테스트 추가: "목적" 같은 상투어 하나만으로는 절대 임계값을 못 넘도록 고정 |
| `scripts/adversarial_eval.py` | 순수 벡터 검색(`store.search`)만 테스트하던 걸 실제 운영 경로(`rag.py`)와 동일한 **벡터+어휘 하이브리드**로 교체 — 이전에는 어휘 계층을 아무리 고쳐도 이 평가에 반영이 안 되는 사각지대였음 |

**검증**: 벡터는 안 건드리고 재인덱싱도 필요 없이, local 백엔드 기준 Layer 2 통과율 32% → 57%, 범위 밖/인젝션/경로유출 오탐 0건 달성.

### 2-2. `EMBEDDING_BACKEND` 설정 키 오타 수정 + sbert 전환

**왜**: `.env`/`.env.example`에 `EMBEDDING_MODEL=sbert`라고 되어 있었는데, 실제
`app/core/config.py`가 읽는 필드명은 `embedding_backend`였음. 즉 **sbert로 전환한다고
설정해뒀던 게 실제로는 한 번도 적용된 적이 없었고, 계속 조용히 local(n-gram 해싱)
백엔드로만 동작**하고 있었음. 인덱스 dimension이 384(local 고정값)인 것으로 확정 확인.

**무엇을 고쳤나**

| 파일 | 내용 |
|---|---|
| `.env`, `.env.example` | `EMBEDDING_MODEL=sbert` → `EMBEDDING_BACKEND=sbert` |
| (환경) | `pip install sentence-transformers` 설치 필요 |
| (작업) | `python scripts/ingest_documents.py`로 384차원(local) → 768차원(sbert) 전체 재인덱싱 |

**주의**: 이 세 가지는 한 세트입니다. 키만 고치고 sentence-transformers를 안 깔면
`RuntimeError`, 재인덱싱을 안 하면 차원 불일치 `ValueError`로 검색 자체가 멈춥니다.

### 2-3. 임계값(`min_document_score`) 재보정

**왜**: 백엔드가 local→sbert로 바뀌면서 점수 대역 자체가 완전히 달라짐(local
0.1~0.4대 → sbert 0.4~0.95대). 기존 0.38은 의미가 없어짐.

**과정 (숫자가 두 번 바뀐 이유를 정리)**

1. `scripts/calibrate_min_relevance.py`로 1차 측정 → 관련 질문 5개/무관 질문 3개
   샘플로 **0.72** 권장 → 적용
2. 실제 `adversarial_eval.py` 28문항으로 재측정하니 **대조군(제일 쉬운 질문)조차
   0.72를 못 넘는** 상황 발견 → 1차 계산에 쓴 표본이 너무 작아서(5+3개) 전체 분포를
   대표하지 못했던 것으로 판명
3. 28문항 전수의 실제 분포(관련 최저 0.437, 무관 최고 0.561)로 **0.58**로 재조정 →
   최종 적용

| 파일 | 내용 |
|---|---|
| `app/agent/state.py` | `EvidencePolicy.min_document_score` 0.38 → 0.72 → **0.58** (최종) |
| `app/agent/nodes.py` | 폴백 기본값 동기화 |
| `app/agent/semantic_router.py` | 주석 갱신 + `SIMILARITY_THRESHOLD=0.45`(라우팅용, 별도 척도)도 local 백엔드 기준으로 잡힌 값이라 재보정이 필요할 수 있다는 경고 추가 (전용 재보정 스크립트는 아직 없음 — 다음 세션 후보) |
| `scripts/adversarial_eval.py` | `MIN_SCORE`를 숫자 하드코딩 대신 `EvidencePolicy().min_document_score`에서 직접 가져오도록 변경 — 이번처럼 값이 바뀔 때 이 스크립트만 갱신을 놓치는 사고 재발 방지 |
| `tests/unit/test_agent.py` | `test_evidence_eval_uses_calibrated_document_score_threshold`가 예전 임계값(0.38)에서만 통과하던 하드코딩 점수(0.5)를 쓰고 있던 진짜 회귀를 발견해 0.8로 수정 |

### 2-4. 스크립트 경로 버그 2건

**왜**: `python scripts/calibrate_min_relevance.py` 실행 시
`ModuleNotFoundError: No module named 'app.mcp'` 발생.

**원인**: `PROJECT_ROOT = Path(__file__).resolve().parent`가 `scripts/` 폴더 자신을
프로젝트 루트로 착각(한 단계만 올라감). 다른 스크립트들(`ingest_documents.py` 등)은
전부 `.parents[1]`(두 단계)로 정확히 계산하고 있었는데 이 파일만 예외였음.

| 파일 | 내용 |
|---|---|
| `scripts/calibrate_min_relevance.py` | `.parent` → `.parents[1]`로 수정 |
| `scripts/adversarial_eval.py` | 같은 버그 + 상대경로(`../data/faiss/...`)로 실행 위치에 따라 깨지던 것도 함께 수정. 이제 프로젝트 루트/`scripts/` 어디서 실행해도 동작 |

**추가**: `[vector]`/`[lexical]` 진단 태그를 verbose 출력에 추가해, 오탐/실패의 원인이
벡터 채널인지 어휘 채널인지 바로 구분할 수 있게 함. 이 태그 덕분에 실제로 "왜 다시
오탐이 늘었나" 원인(faiss_store.py 미적용)을 빠르게 특정할 수 있었음.

### 2-5. 최종 결과

| 지표 | 시작 (local, 미보정) | 최종 (sbert + 하이브리드 + 재보정) |
|---|---|---|
| Layer 2 통과율 | 32% | **71%** |
| 오탐(범위밖/인젝션/경로유출) | 다수 | **0건** |

**남은 것 (다음 세션 후보)**
- recall 실패 4건 (top_k 안에 정답 문서 자체가 없음: 줄임말·어휘격차 2건·다중홉) →
  임계값으로는 해결 불가, 인수인계 문서의 (a)번 방향(청킹 시 상투적 서두 비중
  낮추기, 재인덱싱 필요)으로 이어가야 함
- "거짓전제" 케이스 2건 → 검색 문제가 아니라 답변 생성 프롬프트 쪽 문제일 가능성,
  미확인
- `SIMILARITY_THRESHOLD`(라우팅용, semantic_router.py) 재보정 여부 미확인

## 3. 아키텍처 정리 — 새 MCP 도구 추가 표준 패턴 문서화

**왜**: Jira 연동 같은 새 도메인을 붙이기 전에 "MCP 도구 하나를 추가하려면 정확히
어떤 파일을 건드려야 하는가"가 문서화된 적이 없었음.

**무엇을 고쳤나**

| 파일 | 내용 |
|---|---|
| `docs/team_share/08_mcp_tool_addition_pattern.md` (신규) | 새 MCP 도메인 추가 표준 패턴 문서 |

**주요 내용**
- 전체 구조 다이어그램 (Agent → MCPClient → AsyncMCPPort → 도메인 서버 → 도메인 서비스)
- **코드에 이미 두 가지 패턴이 섞여 있다는 발견**: `data_tools`(purchase/sales)는
  envelope 조립 로직이 `execute_data_tool()` 한 곳에만 있는 좋은 패턴인데,
  `document_tools`는 같은 로직이 `app/mcp/client.py`와
  `mcp_servers/document_tools/server.py` 두 곳에 중복돼 있는 부채 상태. 새 도메인은
  `data_tools` 패턴을 따라야 한다고 명시
- 새 도메인 추가 9단계 체크리스트 (도메인 서비스 → 서버 dispatch → 스키마 등록 →
  `InProcessMCPPort` 분기 → `MCPClient` 메서드 → 권한 정책 → Agent 라우팅 편입 →
  evidence 정책 → 테스트), 실제 파일 경로/코드 스니펫 포함
- 자주 놓치는 지점 정리 (특히 권한 정책 등록 누락은 에러 없이 빈 결과만 나와서
  제일 오래 헤매는 케이스라고 강조)
- `InProcessMCPPort`가 진짜 MCP 프로토콜이 아니라는 한계와, Jira처럼 외부 API를
  처음 붙일 때 생길 수 있는 블로킹 문제를 미리 경고
