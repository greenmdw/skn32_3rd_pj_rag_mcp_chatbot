# 데이터 수집 및 전처리 리포트 (판매·구매 도메인)

- **작성자**: rag_sales 담당 (PM 겸임)
- **목적**: 제출용 산출물인 `ERP_Sales_Data_Full_5y.xlsx`(판매), `ERP_Purchasing_Analytics.xlsx`
  (구매) 두 엑셀 파일이 어떤 원본에서 어떤 과정을 거쳐 만들어졌는지, 그리고 이 파일들이
  MySQL DB로 적재될 때 어떤 전처리를 거치는지 정리한다.
- **근거**: 실제 소스 코드(`scripts/generate_sales_synthetic_data.py`,
  `etl/sales/`, `etl/purchase/`)와 실제 엑셀 파일을 직접 열어 확인한 내용만 담았다.
- **산출물 위치**: (구매)`data/raw/source_data/ERP_Purchasing_Analytics.xlsx`, (판매) `data/raw/source_data/ERP_Sales_Data_Full_5y.xlsx`

## 2. 판매 데이터 전처리 — 원본 보존 + 5년치 합성 증강

판매 도메인은 원본 데이터(70건, 약 1.4년치)만으로는 "5년간 매출 추이" 같은
시계열 질문에 답할 수 없어서, **원본을 절대 변형하지 않고** 그 앞뒤로 합성 데이터를
채워 넣어 2021-08-05~2026-08-04(5년) 범위로 확장했다. 이 작업이 판매 도메인의
핵심 전처리 단계다(`scripts/generate_sales_synthetic_data.py`).

### 2.1 설계 원칙

1. **원본 행은 단 하나도 값이 바뀌지 않는다.** PK(기본키)를 그대로 유지해서, 나중에
   MySQL에 UPSERT해도 원본 70건이 안전하게 보존된다.
2. **새로 만드는 행은 원본에서 실측한 계산 공식·분포를 그대로 따른다.** 예를 들어:
   - 라인 합계 = `ROUND(수량 × 단가 × (1 − 할인율/100), 2)`
   - 라인 세금 = `ROUND(라인합계 × 0.16, 2)` (요르단 부가세 16%)
   - 헤더 소계 = `SUM(라인합계)`, 헤더 세금 = `SUM(라인세금)` — 원본에서 오차 0으로 실측 확인 후 동일하게 적용
   - 원본 데이터의 버그(할인액이 표시만 되고 총액에는 반영 안 됨)까지 **의도적으로 그대로 재현**해서, 증강한 데이터가 원본과 통계적으로 이질적이지 않게 했다.
3. **사업적 서사를 데이터에 반영한다** (PM 승인 사항): 시간이 지날수록 주문 **건수는
   증가**하지만 건당 단가가 작아져 **총 매출은 오히려 감소**하는 구조로 설계 — "과거엔
   소수 인원이 대형 계약 위주, 최근엔 다수 인원이 소액 계약 위주"라는 실제 기업 성장기
   흔한 패턴을 재현.
4. **담당자 풀을 시간에 따라 다르게 한다**: 과거 구간(원본 데이터 이전)은 담당자 풀을
   70→100명으로 넓게 쓰고, 원본이 시작되는 시점부터는 원본과 동일하게 1~70명만
   사용해서 원본과의 접합부가 자연스럽게 이어지게 했다.
5. **고객 이탈을 누적 반영**: 시간이 지날수록 `Is_Active=False`(휴면 고객) 비율이
   누적되도록 생성 — 실제 B2B 거래처가 시간이 지나며 자연 이탈하는 현상을 반영.

### 2.2 검증 — "지어낸 게 맞는지" 확인하는 과정에서 실제로 잡은 오류들

생성 직후 데이터를 다시 검토하는 과정에서 아래 문제를 발견해 재작업했다(실제 발생
이력, 은폐하지 않고 기록).

| 발견한 문제 | 원인 | 수정 |
|---|---|---|
| Index 시트의 행 수 표기가 갱신 안 됨 | 최종 워크북 저장 시 Index 시트를 다시 안 씀 | 저장 직전 각 시트 행 수를 다시 계산해 Index에 반영 |
| `Quantity_Delivered`(배송 수량)에 22%가 NaN | "미배송이면 NaN"이라고 잘못 가정 | 원본을 다시 실측해 실제 규칙(확정/취소/초안=0, 배송완료 계열=전체 수량, 부분배송만 비율값) 확인 후 재생성 |
| `Fulfillment Lines.Quantity_Shipped`가 부분/0값 혼재 | 상태별로 다르게 계산해야 한다고 잘못 가정 | 실측 결과 이 컬럼은 상태와 무관하게 항상 `Quantity`와 동일하다는 규칙을 확인 후 수정 |
| `Sales Forecasts.Accuracy_Percent`가 50~99.99%로 비현실적 | "예측오차 = 100 − 오차율"로 계산 | 실측 결과 이 컬럼은 계산값이 아니라 별도의 독립 랜덤 분포(평균 12.37, 표준편차 7.40)를 따른다는 걸 확인 후 그 분포로 재생성 |
| `Credit Limits.Current_Exposure`(신용 한도 사용액)가 실제보다 훨씬 큼 | 균등분포(0~60%)로 임의 계산 | 실측 결과 실제 사용률 중앙값은 2.3%로 매우 낮고 소수만 크게 쓰는 비대칭 분포(로그정규분포) — 이 분포로 재생성 |

**핵심 교훈**: 처음에 세운 가정을 그대로 코드화하지 않고, 매번 **원본 데이터를 직접
쿼리해서 실측값과 비교 검증**한 뒤에야 확정했다. NaN 비교 시 pandas의 문자열 변환
방식 때문에 생기는 거짓 불일치(false positive)도 별도로 잡아내, 원본 70건이
100% 그대로 보존됐음을 최종 확인했다.

### 2.3 구매 데이터는 왜 증강하지 않았나

구매 도메인은 원본 ERP export(`ERP_Purchasing_Analytics.xlsx`)를 그대로 사용했다.
판매처럼 5년 시계열 요구가 크지 않았고, 원본 규모(발주 50건, 상세 123건 등)로도
Text2SQL 질의응답 시나리오(공급업체별 발주액, 미지급금 등)를 검증하기에 충분하다고
판단했기 때문이다.

## 3. MySQL 적재 전처리 (ETL 공통 파이프라인)

두 도메인 모두 완전히 동일한 4단계 구조를 쓴다(`etl/sales/`, `etl/purchase/`).

```text
엑셀 파일 (ERP export)
  → Extract (추출)
  → Transform (정규화)
  → Validate (검증)
  → Load (MySQL 적재, UPSERT)
```

### 3.1 Extract — 원본을 있는 그대로 읽기

- `pandas.read_excel()`로 워크북의 지정 시트를 읽는다. **값 자체는 전혀 수정하지
  않는다.**
- 유일하게 손대는 부분은 **컬럼명(헤더) 표준화**다 — 원본은 `Customer_ID`처럼
  대문자 스네이크 케이스인데, 이를 소문자로 통일해 이후 스키마 매핑 규칙과 맞춘다.

### 3.2 Transform — 스키마 정규화

| 처리 | 내용 |
|---|---|
| 컬럼명 매핑 | 필요한 경우 원본 컬럼명 → DB 스키마 컬럼명으로 변경 |
| 타입 변환 | 날짜·통화·코드 컬럼을 명시된 dtype으로 캐스팅(예: 문자열 날짜 → datetime) |
| 중복 제거 | `drop_duplicates()`로 완전히 동일한 행 제거 후 인덱스 재정렬 |

구매 도메인은 타입 변환이 실패한 값을 조용히 버리지 않고 경고 로그로 남겨서, 다음
단계(검증)가 그 값을 추적할 수 있게 해둔 점이 판매와 다르다.

### 3.3 Validate — 적재 전 검증

| 도메인 | 검증 기준 |
|---|---|
| 판매 | 필수 컬럼(PK, NOT NULL 컬럼)이 전부 존재하는지만 확인 |
| 구매 | 필수 컬럼 존재 여부 **+ 해당 컬럼에 NULL 값이 섞여 있는지까지** 확인 (판매보다 엄격) |

두 도메인 다 검증에 실패해도 **행을 조용히 삭제하지 않는다** — 오류 목록을 그대로
반환해서 무엇이 왜 걸렸는지 추적 가능하게 한다.

### 3.4 Load — UPSERT 적재 (멱등성 보장)

- 조회용 계정과 완전히 분리된 **쓰기 전용 계정**만 사용한다(판매: `JangGGo`,
  구매도 별도 계정).
- `INSERT ... ON DUPLICATE KEY UPDATE`로 적재해서, **같은 원본 파일로 다시
  실행해도 행 수가 늘지 않는다**(멱등성) — 신규 삽입/갱신 건수를 구분해서 반환한다.
- 스키마에 정의되지 않은 테이블은 적재를 거부한다(허용 테이블 화이트리스트).
- `pandas`의 결측값(`NaN`/`NaT`/`pd.NA`)을 MySQL이 이해하는 `NULL`로 값 단위
  변환해서, nullable 확장 타입 컬럼에서 문자열 `'<NA>'`가 그대로 들어가는 사고를
  방지한다.

### 3.5 실제 적재 결과 (구매 도메인, 실행 확인)

| 테이블 | 적재 건수 |
|---|---:|
| Vendors | 25 |
| Purchase Orders | 50 |
| PO Lines | 123 |
| Invoices | 32 |
| Goods Receipts | 32 |

동일 원본으로 재실행해도 위 건수가 그대로 유지됨을 확인했다(멱등성 검증).

## 4. 요약

1. **판매**: 원본(70건)을 100% 보존한 채, 원본에서 실측한 계산 공식·분포를 그대로
   따르는 합성 데이터로 5년치(800건)까지 증강. 증강 후 여러 차례 재검증을 거쳐
   비현실적인 분포·계산 오류를 수정했다.
2. **구매**: 원본 ERP export를 그대로 사용, 증강 없음.
3. **공통 ETL**: Extract(원본 그대로 읽기, 헤더만 표준화) → Transform(컬럼명·타입
   정규화, 중복 제거) → Validate(필수 컬럼·NULL 검증) → Load(UPSERT, 멱등성 보장)
   4단계로 MySQL에 적재.
4. 판매·구매 두 도메인은 세부 검증 엄격도(NULL 체크 여부)만 다르고 나머지 구조는
   동일하다.
